# 03 数据与执行可靠性

## 1. 数据表设计

PostgreSQL；ID 使用 uuid，时间 timestamptz，金额 numeric(18,2)，业务 JSON 用 jsonb。除不可变事件外，业务主表包含 created_at、updated_at、version。version 用于乐观锁，不能以客户端时间判断先后。

| 表 | 关键字段 | 约束和索引 |
| --- | --- | --- |
| employee | id,employee_no,name,department_id,manager_id,profile_json,status | employee_no 唯一；演示用户不少于 3 人 |
| auth_session | id_hash,user_id,csrf_hash,expires_at | 仅保存高熵 token 哈希；过期索引 |
| conversation | id,user_id,title,active_task_id,last_event_seq | (user_id,updated_at,id) |

与框架 Checkpoint 不强求跨库事务：任务快照保存恢复入口，业务操作台账作为副作用事实源。恢复时对比台账和业务回执，修正落后检查点。

组件、确认、操作、事件均保存 user_id 或可由外键追溯所有权；所有查询在 SQL 层带授权范围。前端隐藏按钮不能代替权限检查。首版单企业，不引入空置租户概念；试点若增加多企业必须全链路补齐 tenant_id。

## 2. 并发与任务队列

消息和动作接收时，在一个事务中保存命令、消息/动作引用、待执行 run 及受理事件，然后返回 202。若提交失败则不返回受理成功。执行器通过数据库领取命令；首版一个进程仍使用持久队列，避免响应返回后任务因内存队列丢失。

同会话执行命令按序推进；数据库租约记录 owner、lease_until 和 fence。租约过期恢复时增加 fence，旧执行者的任务/事件写入通过 CAS 拒绝。业务副作用通过稳定 operationId 幂等，不能只依赖租约防重。

默认租约 30 秒、每 10 秒续租，为设计初值。模型和网络调用在数据库事务外执行，不在等待模型期间持有行锁。关键确认与写入准备采用短事务锁；任务字段修改使用 version 比较。任务处于 EXECUTING/RECONCILING 时，新输入不能覆盖在途写入内容。

## 3. 确认与写入事务边界

确认快照保存：actor、task、动作、排序后的资源 ID、每项版本、字段规范化值、元数据版本、审核意见、hash 和到期时间。默认有效期 15 分钟；服务端使用数据库事实校验。

确认流程：

1. 根据用户调整生成最终预览；旧确认作废，保存新组件和确认。
2. 收到 CONFIRM，检查用户、任务版本、确认状态/到期时间、资源归属和业务版本。
3. 短事务锁定确认，创建唯一 operation，将确认标记 CONSUMED 并绑定 operationId，再提交事务。
4. 事务外调用业务适配器；参数来自确认快照，模型不能临时修改。
5. 持久化回执、更新任务、组件和事件；检查点可稍后同步。

重复确认同一快照返回已有 operation，不创建新操作。内容/意见/范围变化需要新确认；仅重试原操作不需要重复确认。确认过期、权限或版本变化需要重新预览。

模拟提交在业务事务中同时创建 document、workflow、首个 todo、草稿 SUBMITTED 状态及 mock_request_receipt。调用者 operation 台账和业务事务之间仍存在崩溃窗口，用 operationId 查询收敛；不假定恰好一次网络投递。

审批使用 UPDATE approval_todo WHERE id=? AND assignee_id=? AND version=? AND status='PENDING'。影响 1 行才写审批记录并推进流程；否则返回 STATE_CONFLICT。模拟全部为单级审批，同意→APPROVED，驳回→REJECTED；未来多级流程由业务引擎决定，Agent 不自行推导。

批量 operation 包含每项独立 item 和幂等键。默认顺序执行，最高 100 项；单项事务完成，允许部分成功。用户修改内容后对失败项的新审核是新确认/新操作；原失败项网络恢复复用原键。

## 4. 操作状态与结果未知

operation.status 为 PREPARED、IN_FLIGHT、SUCCEEDED、PARTIAL_SUCCEEDED、FAILED_RETRYABLE、FAILED_FINAL、UNKNOWN。UNKNOWN 不是失败，也不能展示为成功。

幂等键按服务端操作身份生成，和参数 request_hash 绑定。同键同参数返回原结果，同键不同参数返回 IDEMPOTENCY_CONFLICT。不能用自然语言全文或每次重试的随机 UUID 作为新键。

业务查询结果规范：SUCCEEDED、FAILED、IN_PROGRESS、NOT_FOUND（仅表示当前没查到，不保证请求从未执行）。写入 UNKNOWN 时先查回执；若业务支持强幂等，可复用原键安全重放；不支持时保持待核实，转人工核实，不能因 NOT_FOUND 就用新键重提。

| 崩溃窗口 | 恢复动作 |
| --- | --- |
| 受理事务提交前 | 客户端同 dedupe key 重试，未受理则新建 |
| 命令已保存、执行器未领取 | 重启后继续领取 |
| 已消费确认、尚未发起调用 | 根据 PREPARED 操作继续，不消费第二次确认 |
| 请求已发出、响应未保存 | 标记 UNKNOWN，按 operationId 核实 |
| 业务成功、任务/Checkpoint 未更新 | 从业务回执和操作台账补齐任务，不重做业务 |
| 已完成、SSE 未送达 | 从事件或快照补发，不重新执行 |

查询操作允许重试，业务写入全部经过上述规则。取消只禁止未发出的后续项；在途项核实完成后展示“停止后续处理，已处理 N 项”，不自动撤销已提交业务。

## 5. 异常策略与预算

| 类别 | 例子 | 策略 |
| --- | --- | --- |
| VALIDATION | 必填/格式/枚举 | 返回 fieldErrors → 收集节点，不做网络盲重试 |
| TOOL_ARGUMENT | JSON/工具 Schema 无效 | 模型修正最多 2 次，仍失败暂停任务 |
| TRANSIENT | 连接复位、502/503/504 | 读请求或有幂等保障的写请求最多 3 次尝试 |
| RATE_LIMIT | 429 | 尊重 Retry-After，无法在剩余预算内等待则持久化待重试 |
| AUTH | session 过期、403 | 不重试，登录恢复后重新校验权限和确认 |
| CONFLICT | 任务/单据版本变化 | 刷新并重新预览，不能模型强制覆盖 |
| BUSINESS_RULE | 超出办理条件等 | 明确说明，只有用户修正可变业务输入后再调用 |
| UNKNOWN_WRITE | 写入超时或响应丢失 | 结果核实优先 |
| INTERNAL | 未分类异常 | 记录 traceId、保存任务、输出恢复入口 |

默认抖动：第 n 次重试随机等待 [0,min(5s,500ms×2^(n-1))]；最多 2 次重试。读取超时默认 10 秒，业务写入 20 秒，模型单次 60 秒；一个 run 自动执行预算 180 秒、最多 8 次模型调用、20 次工具调用。批量待办按独立 item 预算分段推进，总批次默认 10 分钟；暂停等人不占运行预算。所有值可配置并需实测调整。

模型 SDK 内置重试关闭或只由同一适配层统一计数；不能 SDK 3 次 × 网关 3 次。模型输出已流出后重试遵循 message.reset；流式工具请求必须完整落为工具调用记录后才执行。

服务持续失败的依赖采用独立熔断器：设计默认连续 5 次暂时故障后打开 30 秒，半开允许 1 次探测；业务校验错误不计入。后台重试使用 next_retry_at 持久化，不长时间占用线程 sleep。

## 6. 追踪与事件一致性

taskId 跨多轮稳定，runId/traceId 标识本轮，spanId 标识节点/模型/工具。事件记录输入输出摘要、业务编号、attempt、错误码、耗时、能力/Prompt/模型配置版本、字段变化和确认动作。数据库关键状态变更与相应业务事件写入同一事务，事件表同时充当 SSE 可重放来源。

模型和外部调用开始前写 started，调用结束写 completed/failed；进程意外退出留下的 started 在恢复时标记 interrupted 并核实，不补造成功。模型 token 用量只在供应方返回时记录，否则 null，不能编造统计。

证件号脱敏，认证凭证和 Key 永不记录；调试视图也按任务所有权限制访问。默认演示环境保留完整结构化追踪 30 天，业务操作审计跟随业务数据保留，不跟随 SSE 游标过期删除。此保留期是项目默认值，不是企业合规结论。

## 7. 数据迁移和测试边界

业务表使用版本化数据库迁移；框架 Saver 表迁移与业务表分开管理。发布能力不可变，旧任务继续引用原版本。状态 schemaVersion 不兼容时先迁移或禁止自动恢复并说明原因。

重点验证真实数据库事务、CAS、幂等和故障窗口，不编写仅复述字段 getter/setter 的测试。模型决策的自动化测试使用明确标识的测试模型，另保留真实 Qwen 小样本冒烟用例；二者报告分开。
