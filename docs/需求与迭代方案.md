# 国新国际智能小秘：需求与迭代方案

状态：2026-11-11历史需求讨论稿；后续V0.1已实现并在本机模拟范围发布，当前需求、实现差异与验证以 `specs/` 和 `docs/V0.1-验证记录.md` 为准。

详细设计已补充，见 [设计导航](README.md)。已确认需求以本文为基线，工程、协议、数据及验收细节以配套详细设计为准。

## 1. 已确认的目标与范围

- 建设可运行、可调试源码的企业 Agent 工作台，服务模拟与试点。
- 技术主线：Java 原生能力、LangChain4j、LangGraph4j；对话模型通过 Qwen API 接入。
- 暂不建设私有化生成模型部署；需要复现 BGE-M3 + Qdrant + bge-reranker-v2-m3 的 RAG 链路。
- Agent 需要通过多轮对话识别意图、收集资料、补齐字段、调用接口生成单据并提交审批。
- 开发顺序：Agent 主体 → 业务接口发布 → Skill/Workflow/工具封装 → 扩展业务系统和页面。
- 第一版必须可以展示 Agent 主体效果，允许业务接口先模拟。
- 当前统一采用员工身份；用户身份由后端认证会话解析，模型不得指定或更换执行身份。
- 业务范围：出差、报销、因私出国（境）审批、因私证照办理申请；证照办理与借用；个人 OKR；企业政策问答。
- 暂无既有业务资料，由项目设计明确标记为演示用途的制度、单据、用户及评测样例。
- 用户已确认：待办按当前处理人过滤；按自然语言反馈调整范围后返回组件确认，支持语义识别同意或驳回；提单支持草稿；首版无需上传文件，以本人信息和单据必填元数据补齐资料。
- 全部 Agent 流程需要可追溯，接口与工具需要统一异常兜底、参数修复和有限重试机制，作为首版能力。

## 2. 权限与业务语义

个人业务数据仅允许访问当前用户拥有或被授权处理的数据。需要区分：

1. 本人发起或持有的单据、证照、OKR：按当前用户所有权过滤。
2. 本人待审批事项：按当前待办处理人过滤；其单据申请人可能是其他员工。
3. 公共制度：允许所有员工访问；个人资料或受限资料另行设置检索范围。

第 2 项已由用户确认。“本人待办”不能被错误实现为“申请人必须是本人”。员工拥有审批待办由任务分配决定，不必新增固定审批人角色。

认证 session、conversationId、taskId、traceId 分别表示认证身份、对话、业务任务和执行追踪，不能互相替代。所有资源读取、恢复、确认和工具执行均校验当前用户。

## 3. 技术架构建议

先采用模块化单体 Java 后端，减少本地调试成本；前端提供独立的浏览器工作台。页面技术栈后续确定。

| 层次 | 职责 |
| --- | --- |
| 工作台 | 流式消息、历史会话、任务状态、补充资料、确认卡片、结果回执、执行记录 |
| API 与认证 | 解析当前用户、校验资源权限、提供对话及任务接口 |
| Agent Harness | Agent Loop、任务路由、Skill 加载、上下文构建、工具执行、预算与异常控制 |
| LangGraph4j | 状态流转、条件分支、暂停与恢复、Checkpoint、业务 Workflow |
| LangChain4j | Qwen 模型接入、消息和工具协议适配、流式生成 |
| 能力注册 | 业务接口契约、工具白名单、Skill 版本、Workflow 定义、Prompt 版本 |
| 业务适配层 | 同一接口下提供模拟实现和后续真实业务系统实现 |
| 持久化 | 对话、任务、确认记录、执行事件、业务状态、配置版本及评测记录 |
| RAG | 文档治理、切片、BGE-M3、Qdrant、重排、引用、反馈和评测 |

Java 业务代码负责权限、字段校验、状态变更与幂等；模型负责意图理解、参数提取、工具选择和解释。使用 LangGraph4j 统一管理执行状态，避免叠加另一套互相竞争的 Agent 调度循环。

建议 Java 21 + Spring Boot + Maven，业务数据库采用 PostgreSQL；具体依赖版本在开工时通过兼容性验证后锁定，不直接复制不同版本示例中的 API。

## 4. Agent 主体执行模型

基本路径：

接收消息 → 解析身份与任务 → 选择能力 → 加载 Skill/工具 → 理解或更新字段 → 校验 → 缺信息时暂停追问 → 准备操作预览 → 等待用户确认 → 执行工具/Workflow → 检查业务结果 → 输出回执。

查询可以直接执行。正式提交、修改已提交业务、审批等操作经过服务端确认门；用户明确确认后直接办理，无须再要求用户到业务页面重复操作。对草稿的补充和修改属于当前填单任务，用户明确要求保存草稿时直接保存，不逐字段反复确认。

需要覆盖：

- 多轮补充、修改已填字段、取消任务、切换话题后恢复原任务。
- 同一会话可保留多个任务，但默认同一时刻只推进一个写入任务；存在歧义时追问。
- 状态至少包括运行中、待补充、待确认、执行中、成功、部分成功、失败、取消。
- 等待用户时保存状态并释放请求；后续请求通过任务标识恢复，不能阻塞线程等待人工输入。
- Checkpoint 与业务写入是两个层次；恢复图状态不能撤销已发生的业务操作。
- 保存工具调用记录和业务回执；写入前使用业务幂等键，防止重试或恢复造成重复提交。
- 接口超时但是否成功未知时，先按幂等键或请求编号查结果，不盲目重试写入。
- 设置模型调用次数、工具次数、执行时长和上下文预算，处理死循环、无效参数及接口失败。

关键状态建议包含：任务类型、字段及来源、缺失项、候选单据、选中范围、确认版本、已执行步骤、业务结果、当前中断点、Skill/Prompt/Workflow 版本。

## 5. 接口、工具、Skill 与 Workflow

四者分别管理，统一关联版本：

- 业务接口：对外暴露业务能力，定义请求、响应、错误码、权限及幂等约定。
- Tool：供模型调用的受控适配器，使用明确的参数 Schema，自动注入服务端身份。
- Skill：描述适用任务、所需字段、资料要求、可用工具、办理规则、例子和完成条件。
- Workflow：约束关键步骤、分支、确认点及状态变化。

接口先发布契约并可调用验证，再生成 Skill 草稿与工具绑定，校验通过后启用。仅靠 OpenAPI 不足以自动推断全部业务规则；还需要字段、流程及权限元数据。第一版以仓库内版本化配置完成发布与加载，图形化配置后台安排到后续版本。

Skill 先加载目录摘要，确定任务后再加载正文及必要工具，避免全部塞入上下文。Skill 内容不能突破后端权限或确认门，也不直接授予任意网络或脚本执行能力。

模拟低代码公共底座至少包括：单据类型、表单 Schema、枚举与校验规则、单据实例、流程实例、待办任务、审批记录。不在首版建设完整低代码设计器。

## 6. 首版建议的两条演示链路

### 6.1 证照借用申请

用户：我下个月去日本旅游，需要借护照。

系统查询当前用户证照及申请表 Schema，识别为因私出境/证照借用任务；分轮收集明确出行日期、归还日期、用途等演示字段。是否需要同时发起因私出境审批由流程元数据决定，不能仅由模型猜测。

用户补充或修改后，服务端校验字段，发送可修改的申请预览卡片。确认后调用模拟业务接口，真实写入演示数据库并创建流程，返回单据编号、流程编号、当前状态和进度入口。

填单先读取本人资料与表单元数据。姓名、部门等可由可信接口带出；用途、出行时间等由用户提供，不猜测必填值。保存字段来源及资料版本，对无法编辑的身份字段按元数据锁定。后台资料缺失时明确提示并按规则补充，不把用户自述直接写回员工主档。

支持“保存草稿”“先别提交”“继续刚才的申请”，草稿与任务状态均持久化；保存草稿允许缺少正式提交必填项，但校验已填写字段的格式和权限。草稿保存后返回草稿编号和完成情况，正式提交前重新检查表单元数据、资料和单据版本。

完成条件是“已提交待审批”，不等于“审批通过”或“证照已借出”。首版提供模拟流程推进手段，用于演示后续状态查询；完整审批与交接页面后续建设。

### 6.2 本人待办筛选与批量代审核

用户：把上个月的出差待办找出来，我想批量同意。

系统将自然语言转换为明确的单据类型、日期字段、起止时间及待办状态；语义有歧义时追问。相对日期按 Asia/Shanghai 解析，界面展示解析结果。

后端查询分配给当前用户的任务，展示统计、明细及审核范围组件。用户可以勾选、排除、调整筛选条件和审核意见。确认绑定明确的任务 ID、版本、动作、操作摘要和有效期；提交前再次检查任务归属与当前状态。

批量审核逐项返回成功、失败、失效和原因；允许部分成功，仅对可安全重试的失败项重试。范围或动作发生变更后，旧确认失效。

同意、驳回、缩小范围、取消本次操作是不同意图。“不同意这笔报销，金额不对”可以识别为驳回并提取意见；“不对，我只想看上周的”表示调整筛选，不能驳回单据；“先不要处理”表示暂停或取消。歧义时追问，最终组件明确展示条目、同意/驳回动作和审核意见，确认后执行。驳回意见是否必填由流程元数据决定。

默认日期字段采用“待办到达时间”，在组件中明确展示，并允许用户改为单据申请日期等字段。这是可调整设计默认值。

## 7. 工作台与交互协议

首版需要真实可操作的页面：历史会话区域、对话区、任务进度与执行记录区域，以及以下消息组件：

- 文本和流式回答。
- 缺失信息表单；首版不提供文件上传和附件识别入口。
- 单据预览与修改卡片。
- 待办统计、列表及批量范围确认卡片。
- 操作回执、逐项结果及失败重试入口。

服务端通过统一事件协议发送文本增量、任务状态、工具开始/结束、资料请求、确认请求、业务结果和错误。建议 SSE；持久化事件序号支持刷新后重取，断开连接不代表业务操作被取消。

用户看到的是必要的进度和结果；开发视图可展示节点、工具、参数摘要、耗时、错误码与版本。不展示模型内部思维链，不向模型和日志泄露 API Key 或原始认证凭证。

## 9. RAG 与评测设计

文档链路：导入 → 内容解析 → 元数据/版本/权限标注 → 按标题条款切片 → BGE-M3 向量化 → Qdrant 索引 → 发布。

问答链路：问题理解 → 服务端注入授权过滤 → 候选检索 → bge-reranker-v2-m3 重排 → 选择证据 → Qwen 回答 → 引用和反馈。

公共政策与个人资料区分；检索时应用权限过滤，回传前再次校验，检索及答案缓存按授权范围隔离。旧版本政策与生效时间作为显式元数据处理。

没有充分证据时说明不足，遇到冲突时展示依据与适用范围；政策文本不能视为可执行指令。badcase 经归因、修复和复评后发布，不把用户的任意纠正直接作为可信制度。

复现相同的向量化和重排模型，需要独立的可调用推理服务；Qwen 对话 API 不能替代这两个模型。优先接已有托管端点，若无则在 RAG 阶段另定轻量独立服务运行方案。Java 承担业务与编排，不要求模型推理也用 Java 重写。

评测分开发调优集与保留测试集，记录数据、切片、模型、Prompt 和检索参数版本。演示制度和对应评测数据明确标识为模拟资料。

- 检索：Hit@5（前五条是否至少命中一条标注相关证据）、Recall@5、MRR，区分重排前后。
- 问答：答案正确性、证据充分性、引用准确性、无答案时拒答质量；模型评分辅以人工抽检。
- 权限：统计越权问题数、未授权文档命中和泄露次数；零泄露只代表给定测试集观测值。
- Agent：意图和工具选择、参数完整性、任务完成率、确认绕过、重复提交、恢复成功、批量部分失败处理。
- 性能：首字延迟、总耗时、工具耗时、模型调用数与用量。

简历中的 81.7%、92.3%、87.1% 作为原叙述参考，项目报告只填写实际测得结果。

## 11. 全流程追溯

任务保持稳定的 taskId；每次执行或恢复建立 runId/traceId，节点、模型和工具调用记录 spanId 与父子关系，重试保留 operationId 并增加 attempt。用户跨多轮补充仍能串回原任务。

执行事件至少记录：当前用户、会话、任务、节点、开始结束时间、状态、输入输出摘要、字段来源、校验结果、调用工具与接口、错误码、重试原因与次数、确认版本、幂等键、业务单据与流程编号，以及模型/Prompt/Skill/Workflow/表单版本。

同时保存关键状态变更前后差异和 Checkpoint 引用，支持从工作台查看“识别任务 → 获取资料 → 补充字段 → 确认 → 执行 → 回执”的轨迹。参数按字段脱敏，凭证不落日志；操作记录只允许当前用户查看其有权访问的任务。

执行事件落库并支持按任务查询，统一关联普通应用日志。业务操作审计与图 Checkpoint 分别保留；不以检查点回放自动重做写入。首版实现本地可查的完整追踪，不依赖额外建设分布式追踪集群。

追溯目标是解释实际执行过程并定位失败；不承诺非确定性模型调用可以逐字重现，不记录或展示内部思维链。

## 12. 统一异常分类与恢复

工具网关统一处理身份、Schema 校验、超时、异常归一化、重试策略、幂等和事件记录。业务响应使用结构化结果，至少包含 code、category、message、fieldErrors、operationId、businessStatus、data；retryAfter 在适用时返回。是否重试由服务端工具策略和错误类别决定，模型不能任意覆盖。

| 异常 | 处理方式 | 用户侧表现 |
| --- | --- | --- |
| 缺少必填项或字段格式错误 | 返回具体字段和规则，回到资料收集节点；补齐后重新校验和调用 | 保留已填内容，只询问缺失或错误项 |
| 表单元数据变化或枚举无效 | 刷新 Schema，保留兼容字段，重新收集变化项 | 提示需更新的字段；影响提交内容时旧确认失效 |
| 工具参数 JSON/Schema 错误 | 有限次数模型修正，仍失败则保存任务并报告 | 不反复询问用户不需要提供的系统字段 |
| 用户意图、单据或日期歧义 | 暂停并追问或提供候选组件 | 不自动猜测后直接写入 |
| 只读请求连接失败、短暂网络异常、可恢复 5xx | 在总超时内指数退避并增加随机抖动 | 展示重试进度，耗尽后保留任务和重试入口 |
| 429 限流 | 遵守 Retry-After，结合退避与全局重试预算 | 提示服务繁忙；不高频重复请求 |
| 写入超时且结果不确定 | 标记结果待核实，先按幂等键查询；仅在接口支持安全重放时复用原键 | 不误报失败或成功，不生成第二张单据 |
| 登录失效、权限不足 | 停止执行，不自动重复请求；恢复认证后重新校验 | 说明需登录或无权操作，保存可恢复任务状态 |
| 业务规则不满足、单据状态冲突 | 按错误码停止或刷新数据；变化影响范围时重新确认 | 指明不可办理原因，不循环重试相同业务错误 |
| 批量部分失败 | 按条目隔离并记录结果，只重试可恢复的失败条目 | 展示成功、失败、失效清单，成功项不重复执行 |
| 模型服务不可用或工具持续失败 | 达到预算后结束本轮执行，持久化任务；必要时临时熔断对应依赖 | 返回明确失败原因和恢复入口，不伪造业务结果 |
| 未分类内部异常 | 兜底记录 traceId，停止当前危险步骤 | 返回可定位错误，不暴露堆栈、凭证和内部敏感信息 |

建议网络调用最多 3 次尝试（首次 + 2 次重试），示例退避上限按 500ms、1000ms 递增并加入全抖动；实际值按模型与业务接口分别配置。设单次超时、整任务预算和累计参数修复次数；等待用户补充不计入网络重试。

SDK、HTTP 客户端与工具网关明确重试所有权，避免各层独立重试导致次数相乘。取消后不再发起新尝试；已发出的写入需核实最终状态，不能承诺取消一定撤销。

对写入操作，在服务端持久化 operationId/幂等键及请求摘要，模拟业务接口也实现幂等约定。对于同一操作的网络重试复用同一键；若用户修改内容，则作为新操作版本重新确认，不能以旧键提交不同请求。

## 13. 首版新增验收清单

- 当前处理人非本人的待办无法查询、确认或审核；本人业务数据不能跨用户读取。
- 后台本人信息自动带出、字段来源可查；必填项缺失时能够多轮补齐，不能编造值。
- 不完整单据可保存草稿，刷新或重启后恢复，补齐后再确认提交。
- 修改筛选条件、排除条目、同意及驳回语义均可演示；“不对，换个日期”不会变成驳回。
- 同一确认重复点击、同一消息重放、重启后恢复均不会重复提单或审批。
- 注入缺参、无效枚举、网络抖动、429、权限错误、状态冲突和批量部分失败，验证实际分支与最终状态。
- 模拟“业务已成功但响应丢失”，能够通过幂等查询还原结果，不重复写入。
- 每次模型、节点、工具、接口和重试事件均可关联到原任务；关键确认和业务结果有持久化记录。
- 自动重试达到上限后有明确状态与可恢复入口，不发生无限 Agent Loop。

用户已确认权限语义、组件确认、同意/驳回语义、草稿、不上传文件，以及全流程追溯和异常恢复要求。首版两条演示链路和分版本顺序保持前述建议。
