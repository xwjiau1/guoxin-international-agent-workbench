# 规则配置与长期维护

## 职责划分

| 层 | 内容 | 使用方式 |
| --- | --- | --- |
| `AGENTS.md` | 项目硬性范围、安全、环境和交接约束 | 始终遵守，不由其他文档放宽 |
| `CLAUDE.md` | 接管、任务分级、变更入口、项目边界与导航 | Claude 项目指令 |
| `.claude/rules/` | 编码、测试、安全、Agent、Git 五类短底线 | 项目规则；不能用正文中的“触发”冒充路径配置 |
| `docs/project-context.md` | 已核实技术栈、目录、命令、环境和证据边界 | 接管及运行命令前读取，事实变化时更新 |
| `docs/development/` | Spec、团队、工作区等较长流程 | 按 `CLAUDE.md` 触发条件读取 |
| `docs/templates/` | 创建工件时的模板 | 只读所需模板，不将占位符当事实 |
| `specs/` | 版本基线、当前 change、验收和 drift | 按任务读取并持续更新 |
| `docs/V0.1-验证记录.md`、发布清单、`HANDOFF.md` | 已执行证据、产物和当前接管状态 | 只在有实际结果时更新 |

普通 Markdown 链接不等于自动加载；本文件规定的是工作约定，不声称平台一定自动读取所有 rules。文本规则也不能替代权限、Hooks、CI 或数据库约束。

## 修订原则

1. 同类问题重复出现、约束长期稳定且可验证时才新增规则；单次任务事实放 change Spec，已完成事项不无限累积成永久规则。
2. 每类事实保留唯一权威来源。规则只保存必须常驻的底线，详细命令、架构和流程链接到现有文档，避免复制后漂移。
3. 修改规则时检查 `AGENTS.md`、现有 specs 和运维约束，不降低权限、确认、幂等、数据保护及真实验证要求。
4. 技术栈、路径、命令、端口、测试开关和已知限制变化时更新 `project-context.md`；实际验证状态只能由执行证据更新。
5. 定期检查失效链接、重复/冲突规则、过期命令和模板路径。纯文档维护执行链接和差异检查，不虚报业务测试。
6. 不借规则初始化自动安装 Serena、Skills、MCP、子代理或其他工具；如需配置，另按用户授权、实际工具和官方文档验证。

参考规范来源：用户提供的 `personal-dev-system` 通用开发说明（2026-11-12），已按本仓库现有 SDD 和运行约束适配；外部目录不是本项目运行时依赖。
