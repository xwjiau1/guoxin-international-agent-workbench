# Agent 团队与派工

默认由主代理串行承担需求、设计、实现、验证和审查角色；只有用户授权、任务独立且协调成本合理时才并行。角色名称不表示已创建子代理，模型默认继承当前可用配置。

## 职责

| 角色 | 输入与输出 | 边界 |
| --- | --- | --- |
| Lead | 用户目标、Spec、计划、整合与最终交接 | 不越权发布，不仅凭代理自述验收 |
| Product | 场景、范围、权限/副作用、AC | 不自定技术方案，不伪造用户确认 |
| Architect | 模块、数据、契约、兼容、ADR | 不擅改产品目标；保护现有 INV |
| Implementer | 就绪任务、最小代码和回归 | 只写允许路径，不绕过端口/确认门 |
| QA | 分层验证、复现、证据、Bug 子任务 | 不改正确预期凑通过，不混报测试层 |
| Reviewer | 对 Spec、完整差异和证据的独立审查 | 默认只读，问题须有可复现依据 |

## 编码派工必填

- 任务 ID、change/Spec 路径和版本、需求/AC/INV ID。
- 已确认事实、前置依赖、基础提交、契约及不允许改变的语义。
- `main_root`、`worktree_root`、`artifact_root`、分支和独立目录。
- 允许修改文件/目录、禁止范围、共享端口协调人；同一文件只能一个写入者。
- 验证命令、环境、测试层和预期；真实 Qwen/浏览器/外部副作用的授权边界。
- 完成条件与交付格式：文件/提交或补丁、实际测试、风险、未决项和下一接收角色。

不要假定工作代理拥有主对话背景。依赖未就绪、契约未稳定或需操作同一数据库/Docker 执行器的任务不得假装并行。

典型转交：Product → Architect → Lead 拆任务 → Implementer → QA/Reviewer → Lead 整合。失败按四路径回到最上游，不让下游补丁掩盖需求或契约问题。模板见 `docs/templates/agent-handoff.md`，工作区规则见 `git-workspaces.md`。
