## 变更流程与状态门禁

1. 接管：读AGENTS、HANDOFF、验证记录，检查运行环境和未完成工作；不重新安装已有依赖，不覆盖已有数据。
2. SPEC_DRAFT：新增或引用需求编号，说明触发场景、范围、排除项、Given/When/Then和权限/副作用边界。
3. PLANNED：在plan说明模块、契约、数据/配置/版本迁移、重试与兼容性。受影响的不变量必须逐条检查。
4. IMPLEMENTING：在tasks分配文件所有权，按已授权范围实施。共享端口变更先协调，不能多代理并改同文件。
5. IMPLEMENTED：代码存在且可构建，不等于验证通过；记录实现入口与产物。
6. VERIFIED_PARTIAL：运行必要测试并记录命令、环境、范围、结果。gated/skipped不计通过，API桩不替代真实后端，单个模型用例不代表全部意图稳定。
7. VERIFIED：本次变更必需的验收全部有证据，无未处理阻断；否则写明受阻原因和恢复步骤，不能勾选完成。
8. RELEASED：备份及迁移方案就绪，部署对应的新产物，进行smoke/live验收，再更新HANDOFF和验证记录。破坏性操作按AGENTS和用户授权处理；不添加日常修复的重复审批门。

修复已有需求的bug无需重新请求已授权开发许可，但仍应先登记需求编号、回归场景和任务，再改代码。涉及新增业务或改变授权/审批规则时明确范围变化，不能以技术修复名义扩大操作范围。

## 每次交接的最低信息

需求编号；修改文件；契约/数据库/配置变化；测试结果与未执行项；源码对应产物/镜像；部署与回滚；下一个可执行步骤。运行日志在.runtime是本机证据，不应假设新环境已有该目录；可复现命令和结果摘要保存在验证记录。

spec drift按plan中的编号记录，明确“计划能力/当前实现/影响/下一步”。不得只改文案消除实际缺口，也不得把未实现的计划功能描述为已交付。
